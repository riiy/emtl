# P1 · 离线测试体系完善（emtl）

## 0. 文档性质与基线

- 状态：需求（供 OpenCode Plan 使用；不是已批准的实施计划）。
- 工作分支：`refactor/p1-offline-tests`；以当前已合并 P0 的 `master` 为基线。
- 目标运行时：Python 3.11。
- 开始前必须阅读：`AGENTS.md`、`docs/refactor/requirements/P0.md`、`docs/refactor/plans/P0-plan.md`、`docs/refactor/contracts/P0-public-api.md`、`pytest.ini`、`tox.ini`、`.github/workflows/github-actions.yml` 和现有 `tests/`。
- P0 已完成：测试移至仓库根 `tests/`；建立 `conftest.py`、`_offline.py`、Mock、基础行为/日志/契约测试；移除 CI 真实交易账户凭证；独立 Review 报告 41 项离线测试通过。
- 当前 GitHub 主分支的实现应作为事实来源。上述“41 项”是 P0 验收时的基线，不可假定所有测试功能完备，也不要因测试数量增加而视为质量提升。

## 1. 最终目标

在**无真实账户、无真实券商请求、可重复运行**的前提下，建立足以支持 P2 架构重构的回归安全网。优先验证认证、查询、下单、撤单的**请求契约、成功返回、失败传播、无自动重试和无敏感日志**；在 CI 中验证测试执行期确实不能访问网络。

P1 的完成标准是“可以安全地重构”，不是追求代码覆盖率或 Fixtures 数量最大化。

## 2. 范围内任务（按优先级）

### P1-A · 核验并补强现有离线安全网（最高优先级）

1. 审查 `tests/_offline.py`、根 `conftest.py`、`tests/conftest.py` 的安装时机、恢复逻辑、导入顺序及对 `requests` / `socket` / 子进程的适用边界。
2. 保留 P0 已批准的测试入口：仓库根 `python -m pytest` / `python -m pytest tests/`，或仓库外指定 checkout 的绝对 `tests/` 路径；**不恢复 `pytest --pyargs emtl`**。
3. 测试执行期对真实网络连接采取 fail-closed 策略；在 Python 级防护之外，增加至少一次 CI 中的操作系统/容器级断网运行（例如预装依赖后 `docker run --network none`）。安装依赖、构建镜像及 Sphinx 外链检查可单独联网；它们不等同于离线交易测试。
4. 添加负向验证：尝试 DNS 解析、直接 socket 连接、`requests` 请求等，应该确定性失败；必要时覆盖子进程测试入口。测试目标为文档化的自动测试入口，不承诺拦截任意恶意进程。
5. CI 中不注入真实账户 Secrets；用合成父进程凭证检查 `tox` 测试环境变量隔离。禁止日志输出敏感值。
6. 若 CI 层断网实现不具备可行性或会破坏测试运行，Plan 必须列出替代方案和未达成的验收项，不能将“Python Mock 通过”等同于“系统层断网已验证”。

### P1-B · 高风险行为的离线回归测试（最高优先级）

对已有代码进行**特征化测试**，锁定现有可观察行为，不在此阶段重构生产异常或请求流程：

1. `login()`：显式参数与环境变量回退、空值、OCR 空/假值结果、非法 OCR 结果恢复、登录响应非 JSON、缺少验证令牌、认证失败响应、验证令牌提取失败。
2. `_query_something()` / 查询 API：已认证/自动登录、请求 tag 与表单字段、请求返回假值/`None`、非 200 HTTP、超时/连接失败、错误 JSON、业务层非成功 `Status` 时的原样返回。
3. `create_order()`：买/卖参数表单准确性、成功与业务拒绝响应、HTTP 异常、网络超时、响应丢失、响应体异常；每一种可能产生委托的失败，都要断言**不会自动重试**（`session.post` 只能调用一次）。
4. `cancel_order()`：发送前 `strip()`、返回文本的 `strip()`、正常与失败响应、超时与连接断开；明确其当前是否存在重试，并以测试锁定而非改写行为。
5. `get_last_price()`：行情异常状态、缺失/空价格、非法数值、HTTP 失败及是否返回 `NaN`、`0.0` 或传播异常；以 P0 契约和当前代码为准。
6. 日志安全：失败 URL 中的 `validatekey`、Cookie、Authorization、请求/响应正文及异常消息中的合成秘密不得出现在由 SDK 主动生成的日志中；不要求对宿主代码自行打印内容负责。
7. 现有 `_check_resp` 的 HTTP 非 200 裸 `raise` 行为可能产生 `RuntimeError`；P1 先锁定此行为，P3 再决定如何改进异常体系。

不得为了“测试好写”改变原有业务行为。若发现实质资金风险缺陷，单独列为缺陷与阻断建议，先取得批准再改生产代码。

### P1-C · Fixtures 与 Mock 标准化（中优先级）

1. 审计现有测试中的内联 JSON、`Mock()`、`requests.Response` 构造逻辑，消除导致错误的重复实现；**不要为每个小响应机械建立文件**。
2. 优先为登录成功/失败、资产、订单、交易业务拒绝、撤单、无效响应等稳定且会在 P2 重用的协议案例建立 `tests/fixtures/`，可选地引入 `tests/helpers.py` 或 pytest fixture 工厂。
3. 默认使用**人工构造的合成数据**。如果有经过人工采集和脱敏的真实响应，仅在确认无任何账户、令牌、Cookie、持仓敏感信息、真实订单标识或可还原映射后才允许入库。禁止在 CI 或 Agent 中抓取真实响应。
4. 为关键 Fixtures 校验字段/类型及必要的跨响应关联关系；保持券商协议的原始键名、大小写与错误码，避免脱敏后产生不真实的测试。
5. Fixture 命名描述业务状态，测试明确断言请求内容、响应解释及副作用，而非只断言“不抛异常”。

### P1-D · CI 与质量反馈（中优先级）

1. 保持现有 tox 和 Python 3.11 主测试入口；增加明确标记的离线/网络验证步骤，不要让在线 `docs linkcheck` 与离线交易测试混淆。
2. CI 在干净 checkout 及无账户密码的环境中自动运行。至少执行一次系统/容器层断网的**完整离线测试集**，并在日志中清楚体现通过/失败结果。
3. 输出 `pytest` 测试明细及 `pytest-cov` 的行/分支覆盖率，记录 P0 基线与 P1 增量；关键路径通过率优先于总覆盖率数值。
4. 检查测试顺序随机性/状态污染：隔离 `_em_validate_key`、Session Mock、OCR 替身、环境变量和 logging 捕获；至少用两种测试顺序或独立进程运行验证关键测试。
5. 避免新增不必要的第三方测试框架；若引入 `pytest-socket` 等依赖，必须说明其与现有 `_offline.py` 的互补性，不能造成双重维护且无新保证。

## 3. 不在本阶段的工作

- 不引入 `TradingClient`、新 Auth/HTTP/Trading 模块、多账户并发锁或生产级会话生命周期（P2）。
- 不统一异常类、不改变非 200 的既有抛错方式、不改返回值 Schema、不新增类型封装（P3）。
- 不修改旧的 `create_order`/`cancel_order` 签名、请求参数、实盘默认行为或成功返回类型。
- 不在下单、撤单或未知状态的请求上增加自动重试。
- 不直接连券商、不调用真实订单、不使用真实账户凭证、不自动发布。
- 不为纯覆盖率指标加入没有业务断言价值的测试。

## 4. Plan 阶段要求

Plan Agent 必须在只读状态完成：

1. 从当前仓库代码和测试开始，建立“已覆盖 / 有缺口 / 不属于 P1”的风险测试矩阵，逐项标注文件和被测函数。
2. 分别列出“新增用例”和“可能删除/合并的冗余用例”，优先复用 P0 已有安全隔离设施。
3. 为 P1-A/B/C/D 给出按小批次执行的文件清单、具体测试场景、预期断言和 CI 改动。
4. 明确 OS 级断网测试实施方式、依赖安装与测试执行的隔离边界、验证命令。
5. 针对真实请求协议细节无法可靠确定的场景写出“未知、待证据”，禁止臆造真实响应数据。
6. 对每个步骤给出验收条件、已知风险、失败时的停止条件以及回滚方法。
7. 输出一份与聊天上下文无关的完整计划，目标为 `docs/refactor/plans/P1-plan.md`；**Plan 不改动代码**。经人工批准后由 Build Agent 仅保存计划文件。

## 5. Build 阶段要求

1. 读取 `AGENTS.md`、本文件及已批准的 `docs/refactor/plans/P1-plan.md`。
2. 按计划先完善高风险测试，再提取必要的 Fixtures/公共帮助函数，最后调整 CI；每批运行相关离线测试。
3. 测试只能使用合成数据和 Mock，必须断言网络调用次数、表单/URL、原样响应与异常传播。
4. 在禁网环境运行完整测试集，记录命令、Python/tox/pytest 版本、退出码；网络依赖安装在禁网执行前完成。
5. 遇到必须修改生产逻辑才能通过的新缺陷时，先停止相应改动并单独列出问题；没有人工授权不得改变生产语义。
6. 不自动 `commit`、`push`、`tag` 或发布。
7. 最终报告：新增/修改文件、测试矩阵覆盖情况、各验证命令真实结果、失败或缺失证据、剩余风险及预计 P2 可复用的测试资产。

## 6. Review 阶段要求

只读审查全部 tracked、staged、untracked 改动，并核实被忽略的计划/需求是否会漏交付。重点证伪：

1. 是否存在绕开网络防护而访问真实接口的自动测试路径，或者 CI 声称“系统禁网”但未实际运行。
2. 测试是否 Mock 了真正需要测试的函数，造成假覆盖；是否仅验证 Mock 自身调用。
3. 下单/撤单超时或响应丢失场景是否错误地自动重试或被错误判断为未下单。
4. Fixtures 是否有真实身份、资产、订单、认证或可还原敏感信息；是否扭曲重要协议字段。
5. 测试间共享 `_em_validate_key`、Session、OCR、日志和环境变量是否引起相互污染。
6. 旧的公共 API 签名、成功返回结构、实盘运行语义是否发生未批准变化。
7. CI 是否会让真实凭证从 Secrets、父进程或 tox 环境穿透到测试进程。
8. 覆盖率数字是否掩盖关键异常路径的缺失。

输出 `PASS` / `FAIL` / `NEEDS EVIDENCE`、文件/行号、最小复现、阻断与非阻断建议。不直接修改代码。

## 7. P1 验收标准（必须满足）

- [ ] P0 已有的安全测试和公共 API 契约测试全部继续通过，不减少既有保护。
- [ ] 登录、查询、下单、撤单的高风险成功/失败矩阵有明确、有效的离线断言；OCR 空结果等 P0 遗留分支已补充或给出有证据的排除理由。
- [ ] 订单提交请求抛超时/连接错误、响应不确定时，不会自动重复发送；对应测试检查实际 POST 次数。
- [ ] 已建立**最小充分**的复用 Fixtures/响应工厂，且没有真实敏感数据入库。
- [ ] 所有支持的自动测试入口均无真实网络请求；CI 至少一次在系统/容器禁网条件下运行完整离线测试集并通过。
- [ ] CI/test/tox 不注入或传播真实账户凭证；合成凭证隔离检查通过。
- [ ] 至少重复执行两次测试或在不同顺序下运行关键集合，未发现共享状态污染和不稳定失败。
- [ ] 测试、覆盖率、网络隔离和 CI 检查保留可复现的命令、工具版本及退出码。
- [ ] 旧公共 API 签名、成功返回值及真实交易语义保持不变；没有 P2/P3 范围扩张。

## 8. 交付物

- `docs/refactor/plans/P1-plan.md`：Plan 后批准的独立实施计划。
- `tests/`：风险驱动新增和调整的测试，必要时包含 `tests/fixtures/` / `tests/helpers.py`。
- `.github/workflows/`、`tox.ini`、必要时测试专用容器定义：清晰的离线 CI 验证流程。
- `docs/refactor/` 下简短的 P1 验收记录：测试矩阵、验证命令、结果和遗留风险。
- 不要求发布，也不要求生产代码架构重构。

## 9. 停止条件

一旦验收清单满足、独立 Review PASS、远端 CI 通过，即停止 P1 并进入 P2。新增框架、大范围风格清理、追逐总覆盖率、冗余参数组合均不构成延迟 P1 合并的理由。遇到网络隔离无法验证、真实交易误触风险、关键测试假覆盖或兼容性变化时，停止并解决阻断后再继续。
