# P4 · 持续发布与维护（emtl）

> **状态：需求草案，供 OpenCode Plan 使用；尚未批准实施。**
>
> 建议分支：\`refactor/p4-release-maintenance\`。Plan 开始时必须重新核实最新 \`origin/master\`、分支 HEAD、工作区状态和本文件版本；不得将本文创建时的 SHA 冒充后续基线。
>
> **阶段目标：** 在 P0–P3 已通过的基础上，建立可重复、可审计、可回滚的 Alpha/Beta 验证、兼容性管理、正式发布和持续维护流程。
>
> **安全边界：** 所有 CI 和自动化测试继续使用合成数据并保持系统级禁网。禁止在 CI、构建、发布或自动化维护任务中使用真实账户凭证、访问券商接口或执行真实交易。任何真实账户验证必须另行说明目的、范围、风险和授权，不属于本需求的默认授权。

## 1. 背景与目标

P0–P3 已完成并归档为 PASS。P3 之后，Read the Docs 文档构建问题已通过独立修复验收；当前文档交付方向为 HTML + RST + Sphinx，不提供 PDF/EPUB 下载产物。

P4 关注项目从“重构完成”进入“可持续维护和发布”的工程闭环。目标不是增加新的交易功能，而是让维护者能够：

1. 在干净环境中构建、安装、验证项目及其发布产物。
2. 在明确的 Alpha/Beta 准入和退出条件下收集反馈。
3. 对外准确声明 Python、操作系统和依赖兼容范围。
4. 以可审计的版本、变更记录和发布流程交付包。
5. 在发布失败或发现回归时，能够停止发布、撤回/标记问题版本并发布修复版本。
6. 通过低维护成本的 CI、依赖和问题处理机制持续维护项目。

**优先级：** 发布正确性与交易安全边界 > 可安装性和兼容性证据 > 版本交付可追溯性 > 维护自动化便利性。不得为了追求发布自动化而放宽既有安全门槛。

## 3. P4-A · Alpha 验证

### 3.1 目标

建立发布候选版本的内部验证门槛，证明源码、sdist、wheel 和干净环境安装路径之间一致。

### 3.2 必须覆盖

1. 从干净 checkout 构建 sdist 和 wheel，不依赖开发机遗留的 \`dist/\`、\`build/\`、editable install 或本地生成文件。
2. 检查两个产物的文件清单、包版本、依赖元数据、entry point、license、README/Changelog 和必要 package data。
3. 在全新虚拟环境中分别从 wheel 和 sdist 安装；不能只验证仓库根目录下的 import。
4. 从安装后的环境执行最小 smoke tests：
   - \`import emtl\` 和 \`from emtl import TradingClient\`。
   - 检查既有包级 API/CLI 导出和版本信息。
   - 执行 \`emt --help\` 或等价 CLI 无副作用入口。
   - 确认导入、帮助和客户端构造不会发起网络请求或真实登录。
5. 在合成替身和禁网环境中运行既有测试；P0–P3 的安全、账户隔离、交易异常和无自动重发断言不得弱化。
6. 验证安装产物不包含测试凭证、临时日志、覆盖率文件、构建缓存、开发机绝对路径或非交付证据。
7. 记录构建命令、工具版本、产物 SHA256、文件清单和安装测试结果。

### 3.3 Alpha 准入与退出

- 准入：代码 Review 和必需 CI 通过；候选版本号、变更记录和兼容目标已由维护者确认。
- 退出：sdist/wheel 均可在干净环境安装；最小 smoke tests、离线测试及包内容审计通过；没有未解释的高严重度问题。
- 任一产物缺文件、版本不一致、导入副作用、自动网络访问或交易安全回归，均为 FAIL，不进入 Beta。

Alpha 可以先作为内部构建候选，不要求立即上传 PyPI 或公开分发。

## 4. P4-B · Beta 验证

### 4.1 目标

以受控、可退出的方式收集真实使用环境反馈，验证安装、文档、API 易用性和错误可诊断性；不以真实交易成功作为默认验收标准。

### 4.2 Beta 机制

Plan 必须先比较低成本选项，例如 GitHub Pre-release、受控测试包或 PyPI pre-release，并推荐一个最小方案。不能在没有维护者批准时创建公开发布或上传包。

Beta 说明至少包含：

- 版本号、发布日期、适用 Python/OS、安装方式和已知限制。
- 本次变更、潜在兼容性变化、升级/降级方法。
- 不得将 Beta 当作生产稳定性或券商协议正确性的保证。
- 问题反馈模板：环境版本、最小复现、脱敏日志、预期/实际行为。
- 明确禁止提交密码、验证码、Token、Cookie、账户标识、完整请求/响应和其他个人敏感数据。

### 4.3 真实账户边界

- 自动化 Beta、CI 和回归测试必须使用合成账户与 Mock，保持网络禁用。
- 不要求 Beta 用户提交账户凭证或交易记录。
- 不把真实下单、撤单或成交作为 Beta 自动验收步骤。
- 若维护者未来确实需要真实券商验证，必须另行定义只读/写入范围、人工操作、金额限制、风险告知、数据脱敏和停止条件，并取得明确授权；这不由 P4 默认授权。
- 不提供自动补单、自动重试或自动交易恢复能力。

### 4.4 Beta 退出条件

- 反馈经过分类：安装/环境、文档、API 兼容、功能缺陷、安全问题。
- 所有阻断发布的问题已修复或明确延期并披露。
- 没有未解决的敏感信息泄漏、重复交易风险、账户串扰或公共 API 意外破坏。
- 维护者明确批准进入正式发布；Beta 测试人数或时长不作为唯一成功指标。

## 5. P4-C · Python、操作系统与依赖兼容性

### 5.1 支持矩阵

1. 以 \`python_requires\`、classifiers、tox 和 CI 实际测试矩阵建立一张统一支持矩阵。
2. 先确认项目真正需要支持的 Python 最低版本及候选版本；当前 Python >=3.10 声明与只测试 Python 3.11 的现状必须显式处理。
3. 只将通过安装、核心离线测试和构建检查的版本标记为已验证；未运行的版本不得标记为 tested。
4. 操作系统同理：当前 Unix/POSIX classifiers 不等于所有 Unix 发行版均已验证；没有 CI 证据的 Windows/macOS 不得宣称正式支持。
5. 优先选择能改变支持声明或用户决策的最小矩阵，不为追求矩阵数量而无差别扩张。

### 5.2 依赖维护

- 生成运行时、构建、测试、文档依赖的清单，明确直接/间接依赖和来源。
- 检查已知安全公告、弃用、Python 兼容性和上游维护状态。
- 对每项依赖更新说明原因、版本范围、风险和验证方式。
- 精确 pin、范围约束或锁文件的策略由 Plan 根据包库用途和现有工作流决定；不得为了“现代化”一次性升级所有依赖。
- 依赖升级必须通过离线安全测试、兼容性矩阵、包构建及文档构建；对可能改变 HTTP/交易行为的 requests/urllib3 更新，增加定向请求次数、重定向和异常回归验证。
- 建立轻量依赖审查节奏和安全问题响应流程；不强制引入新的第三方 SaaS 或复杂自动化平台。

### 5.3 兼容性与弃用

- 定义公共 API/CLI 的兼容承诺：签名、参数、返回值、异常、CLI 参数及退出码。
- 明确新增、弃用和移除 API 的流程；任何破坏性变更必须有单独批准、迁移说明和版本策略。
- 对每个正式发布候选执行 API/CLI 契约测试。
- 不把内部实现细节承诺为公共 API；但 P0–P3 已明确锁定的行为不得被 P4 无声改变。

## 6. P4-D · 版本构建与正式发布

### 6.1 版本与变更记录

Plan 必须提出并经维护者批准：

- 版本号方案：与现有 setuptools_scm/tag 工作流兼容，并说明 alpha/beta/rc 与稳定版本如何表示。
- 版本来源：Git tag、源码归档、wheel 元数据和运行时 \`emtl.__version__\` 必须一致。
- Changelog 规则：用户可见功能、修复、安全变化、兼容性变化、弃用和已知限制。
- 发布 tag 的命名和不可变规则；禁止通过覆盖已发布 tag 或重用版本号修复错误。

### 6.2 发布前检查

每次正式发布至少要求：

1. 发布候选来自已合并的 master，工作区干净。
2. 必需 Build、check、docs、Offline tests 全部成功。
3. 最终提交 SHA 与受测提交对应；若有合并提交，核对代码树。
4. sdist/wheel 在干净环境构建、安装并通过 smoke tests。
5. 检查包元数据、版本、依赖、文件清单和 SHA256。
6. Changelog、README、文档、GitHub Release notes 一致。
7. 不包含真实账户秘密、CI token、测试输出、开发机路径或未授权数据。
8. 发布权限和凭证使用最小权限；优先沿用已配置的 PyPI Trusted Publishing，不新增长期 API token。
9. 发布触发条件必须明确验证 tag 与版本对应关系、目标分支/提交和所需审批；Plan 应特别审查当前 tag 触发即发布的 workflow 风险。
10. 维护者明确批准正式发布。Plan 和 Build 不得自行上传 PyPI、创建正式 release 或推送 tag。

### 6.3 发布执行与产物

- 正式发布产物至少包括 sdist、wheel、版本信息、SHA256 和发布说明。
- 记录 Git commit、tag、构建 workflow、Artifact、包文件哈希和 PyPI 页面。
- 发布后在干净环境从正式包源安装指定版本并运行无副作用 smoke tests。
- 发布 workflow 必须能区分 PR 检查、预发布和正式发布；PR 不得获得发布权限。
- 对不可变包版本不尝试覆盖上传；发现问题时按下节流程处理。

## 7. P4-E · 发布失败、回滚与 Hotfix

### 7.1 失败分类

Plan 至少区分：

- 构建/测试失败：停止发布，不创建正式 tag。
- 产物错误但尚未上传：修复后重新构建，使用新候选。
- 上传失败或发布状态不确定：先核实 PyPI/GitHub 实际状态，禁止盲目重复发布。
- 已发布版本存在缺陷：评估 yanking、安装提示、GitHub Release 标注及 Hotfix；不能删除或覆盖已发布版本作为默认方案。
- 安全或交易风险缺陷：优先停止推荐/使用该版本，发布安全公告和修复版本；是否撤销/标记版本由维护者决定。

### 7.2 回滚与 Hotfix

- 定义上一个已知良好版本的安装回退命令及适用限制。
- 明确数据库/本地状态（若无则记录无状态）和外部券商状态不能通过 SDK 回滚。
- Hotfix 必须从受影响稳定版本或 master 的明确基线创建，增加最小回归测试，运行完整必需 CI，再发布新的唯一版本号。
- 回滚软件包不等于撤销已发生的券商订单或资金变化；不得暗示 SDK 能自动补偿真实交易。
- 发布故障和安全问题应有时间线、影响版本、缓解措施、修复版本和复盘记录。

## 8. P4-E · 持续维护与工程复盘

维护流程应足够轻量，至少覆盖：

1. Issue/PR 分类：安全、交易风险、功能缺陷、兼容性、文档、依赖和使用问题。
2. 安全问题处理：避免在公开 Issue 中要求用户提交凭证或敏感日志；必要时提供私密报告渠道。
3. 依赖审查：定期检查直接依赖安全公告和维护状态；更新前进行影响评估和针对性回归。
4. CI 维护：保证 Build、check、docs、Offline tests 的状态可见；失败时保留可诊断 Artifact。
5. 文档维护：在线 HTML 文档、安装说明、兼容矩阵、Changelog 和发布说明保持一致。
6. 版本支持：明确当前稳定版、Beta 版和旧版本的维护/安全修复政策；不承诺未经资源支持的长期维护期限。
7. 工程复盘：记录发布耗时、失败原因、回滚/Hotfix、用户反馈和新增维护负担；只改进确实影响可靠性或维护成本的流程。

不要求引入新的数据库、消息队列、遥测、用户追踪或商业监控服务。

## 9. P4 验收矩阵

| 领域 | 最低验收证据 | 阻断条件 |
| --- | --- | --- |
| Alpha 构建 | 干净 checkout 的 sdist/wheel、文件清单、版本和 SHA256 | 构建失败、缺包、版本不一致、夹带秘密 |
| 安装 | 两种产物分别在干净 venv 安装 | 只能 editable 安装、导入失败或依赖元数据错误 |
| Smoke tests | import、公开 API、版本、CLI help；确认无网络副作用 | 构造/帮助命令触网或交易 |
| 兼容矩阵 | 每个声明支持的 Python/OS 均有真实 CI 证据 | 声明超出测试范围、关键版本失败 |
| 离线安全 | Offline tests 继续禁网，P0–P3 保护节点保留 | CI 可访问券商网络、凭证注入、交易重发或账户串扰 |
| Beta | 候选说明、反馈模板、问题分类和退出决策 | 未披露限制、要求提交秘密、阻断缺陷未处理 |
| 正式发布 | 受测 SHA、tag、Build/Offline CI、产物哈希、审批和发布记录 | PR 可发布、tag/版本不匹配、无审批、Artifact 不可追溯 |
| 安装后验证 | 从正式包源安装指定版本并执行无副作用 smoke tests | 发布包无法安装或版本不一致 |
| 回滚/Hotfix | 可执行回退说明和至少一次不发布真实包的演练/桌面推演 | 回滚步骤不明确或误称可撤销真实交易 |
| 文档 | Sphinx HTML 与 Read the Docs 构建成功，安装/兼容/变更说明一致 | 文档缺失、死链或与实际支持范围冲突 |
| 维护 | 依赖审查、Issue/安全反馈、CI 失败处理和复盘流程有责任人/触发条件 | 只有自动化工具而没有可执行责任流程 |

测试数量、覆盖率或 CI job 数量不能单独作为 P4 PASS 依据；验收必须对应上表的实际风险和用户可观察行为。

## 10. 明确不在 P4 范围

- 不开发新的交易功能、策略、行情分析、自动化下单、自动补单或订单对账。
- 不把真实账户登录、真实下单/撤单或资金结果作为 CI、Alpha/Beta 或正式发布自动门槛。
- 不改变 P0–P3 的安全、账户隔离、异常、单次发送和旧 API/CLI 兼容契约；发现问题应先停止并单独评估。
- 不进行与发布维护无关的架构重写、异步化、分布式锁、服务端化或 UI 开发。
- 不为追求“最新”而整体升级依赖、打包工具、Sphinx 或 GitHub Actions。
- 不无证据地宣称支持所有 Python 版本、所有 POSIX 系统、Windows、macOS 或 PyPy。
- 不在本需求阶段默认批准 PyPI 正式发布、推送正式 tag、修改 PyPI Trusted Publisher、使用真实账户或产生真实交易。
- 不强制迁移 RST 到 Markdown；文档维持 HTML + RST + Sphinx。

## 11. Plan 必须先解决的维护者决策

Plan 应把未知事项整理为简短决策表，区分“可从仓库/公开元数据验证”与“必须由维护者选择”。至少包括：

1. **Python 支持矩阵：** 最低版本是否继续为 3.10；哪些版本作为正式支持；每个版本是否有依赖支持和 CI 证据。
2. **操作系统范围：** 是否只声明 Linux/Unix，是否值得验证 macOS/Windows；没有证据时保持未声明。
3. **发布目标：** 是否继续 PyPI；稳定版和预发布是否都使用 PyPI；是否需要 GitHub Pre-release。
4. **版本策略：** setuptools_scm/tag 规则、PEP 440 预发布标识、稳定版本号与 Changelog 规则。
5. **发布授权：** 谁能创建 tag、谁批准 PyPI 发布、是否使用现有 Trusted Publishing environment approval。
6. **Beta 方式：** 内部 Alpha、有限外部 Beta 或直接发布候选；参与者如何反馈和退出。
7. **维护承诺：** 依赖审查频率、Issue 响应预期、旧版本支持期限；避免承诺超过维护能力的 SLA。
8. **真实账户验证：** 默认不需要；若确需进行，必须单独授权，不得把它隐含在 P4 计划中。

不得因这些问题尚未决定而停止只读调查；Plan 应先给出有证据的推荐选项，再请求维护者批准真正影响资金、对外承诺或发布权限的决策。

## 12. Plan 交付要求

\`/emtl-plan P4\` 应生成完整、自包含的 \`docs/refactor/plans/P4-plan.md\`，至少包括：

1. 当前 master SHA、工作区状态、仓库发布/CI/包元数据/文档基线。
2. 当前发布链路图：tag → build/test → package → PyPI → docs；指出现有 workflow 的触发、权限和产物风险。
3. Alpha/Beta 的准入、退出、反馈和停止条件。
4. 支持 Python/OS 矩阵及证据缺口，不把未验证版本列为支持。
5. sdist/wheel 构建、内容审计、干净安装、CLI/API smoke tests 的具体命令。
6. 版本号、tag、Changelog、GitHub Release、PyPI Trusted Publishing 的一致性策略。
7. 发布失败、状态不确定、yank、Hotfix 和回滚步骤。
8. 依赖、安全、Issue、文档和 CI 的轻量维护机制。
9. 明确的文件修改清单、风险、成本、回滚方式和阶段依赖。
10. 每一阶段的可执行验收命令、原始证据位置、远端 CI/Artifact 关联方式。
11. 需要维护者批准的决策清单；Plan 不等于 Build 授权。

Plan 必须优先复用现有 setuptools_scm、tox、GitHub Actions、PyPI Trusted Publishing、Sphinx 和 Offline tests。若现有设施足够，不增加新工具或服务。

## 13. Build、Review 与阶段关闭边界

- **Plan：** 只读检查并创建自包含 P4 Plan；不修改生产代码、配置、版本、tag 或发布状态。
- **人工批准：** 维护者先审查支持矩阵、发布触发/权限、Beta 机制、版本策略和真实账户边界，再批准具体阶段。
- **Build：** 仅实现已批准的 P4 Plan；Alpha、Beta、兼容矩阵、发布工作流和维护机制分批验收。不得自行上传 PyPI、创建正式 tag 或发布 GitHub Release。
- **Review：** 使用独立 Session 审查 requirements、批准 plan、tracked/staged/untracked、构建产物、兼容性证据、权限和回滚流程；明确输出 PASS / FAIL / NEEDS EVIDENCE。
- **远端验收：** 最终 PR 的 head SHA 对应必需 CI；Artifact 包含构建日志、JUnit、coverage、包文件清单和哈希。合并后核对受测代码树与合并代码树。
- **发布授权：** 即使所有自动检查通过，正式 PyPI 上传、正式 tag 和 GitHub Release 仍需维护者单独明确批准；本文件不授予该权限。

### P4 结束条件

只有当以下事项全部成立，才可宣布 P4 PASS：

1. Alpha 验证通过，sdist/wheel 在干净环境可安装且内容正确。
2. Beta 已按批准方式完成，阻断问题处理完毕或有明确披露和延期批准。
3. Python/OS 支持矩阵与实际 CI 证据一致。
4. 版本、Changelog、tag、构建产物和发布元数据一致。
5. 发布流程具备权限边界、产物追溯、失败处理和 Hotfix/回滚说明。
6. 持续维护流程有实际责任人、触发条件和最小可执行步骤。
7. P0–P3 的安全与兼容保护继续通过。
8. 最终独立 Review PASS，最终提交远端证据闭环。

完成后停止 P4，不以增加更多自动化平台或测试矩阵作为继续扩张理由。
