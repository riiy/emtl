# P3 · 交易异常语义与不确定结果处理（emtl）

>

## 1. 目标与非目标

**目标：** 让显式 `TradingClient` 的调用者在发生异常时，安全地辨别两类情形：

1. **能够确认没有进入该次交易 POST**：例如客户端已关闭、认证前置失败、输入校验在发单前失败；不得宣称交易结果未知或已经受理。
2. **已经进入或试图进入该次交易 POST，但无法确认券商最终结果**：例如传输异常、响应缺失、非成功 HTTP、未跟随的重定向、下单两次 JSON 解码中任一步异常、撤单文本解码异常；必须提供机器可识别的“结果未知”信号，明确禁止据此自动重发。

“交易 POST 已尝试”仅表示调用方已进入发送边界，不证明数据包已送达、券商已受理或成交。对无法区分发送前后状态的连接异常采取保守分类，不推断成交与否。保留明确返回的合成业务响应原样，不凭猜测解释券商业务 `Status`。

**本阶段优先级：** 正确的资金风险语义 > 旧 API 兼容 > 最少代码与测试变更 > 统一异常体系的完整性。P3 完成后，调用方可以暂停自动化交易、人工核对；本阶段不做自动对账或恢复交易。

## 2. 已核实的代码基线

- `src/emtl/_protocol.py::check_response()` 在 `resp.status_code != 200` 时调用固定日志，然后使用裸 `raise`，正常调用可能得到 `RuntimeError("No active exception to reraise")`。该函数同时服务旧 `core` 和新 `TradingClient`。
- `src/emtl/client.py::TradingClient` 已实现显式账户绑定、独占 Session/Cookie/token、同账户跨实例 RLock、新认证失败清状态与 `close()`；`create_order()`、`cancel_order()` 经 `_query_something()` 和共享 `_protocol.query()` 发 POST。
- 新客户端订单/撤单设置 `allow_redirects=False`；请求异常不会自动重试、补单或重新认证后重发。首次使用客户端时，认证 POST 可能发生在交易 POST **之前**，两类 POST 不得混淆。
- 下单成功路径保留 **两次** `resp.json()` 求值并返回第二次结果；撤单成功路径保留 `resp.text.strip()`；业务 `Status` 与撤单文本不由 SDK 解释。
- `src/emtl/core.py` 的九项旧包级函数、私有测试接缝和 `core.get_last_price()` 仍受 P0/P1/P2 兼容契约保护；旧认证保留旧 token/业务 Status 处理特点，旧订单 HTTP 行为不自动等同于新客户端。
- P2 最终 PR #5 已合并；远端 CI 最终受测提交 `6e2078f7dce9f255d60ce89699d405efc09e0e2f`，其与合并提交的 Git Tree 一致；三种测试入口各 **350 passed**。这只是历史基线，P3 必须重新验证最终代码。

Plan 必读：`docs/refactor/contracts/P0-public-api.md`、`docs/refactor/contracts/P2-client-api.md`、P1/P2 需求、批准计划与验收报告、`src/emtl/{core,client,_protocol}.py`、`tests/test_orders.py`、`tests/test_client_operations.py`、`tests/test_client_auth.py`、`tests/test_api_contract.py`、根测试隔离设施及 CI 工作流。

## 3. P3-A · 先批准最小错误契约（最高优先级）

Plan 必须独立比较最小可行设计，至少明确以下候选，而不是把它们当作已批准实现：

- **交易结果未知异常**：建议公开稳定类型 `TradeOutcomeUnknown`（名称可在 Plan 确认）。只用于新 `TradingClient.create_order()` / `cancel_order()` 的业务 POST 进入发送边界后，因故无法确认结果的情形。
- **明确 HTTP 错误**：建议新客户端使用 `BrokerHTTPError`（或同等名称）替代裸 `raise`，暴露可安全读取的整数 HTTP 状态码；交易 POST 的 HTTP 非 200 应优先映射到“结果未知”，不能仅因 `4xx/5xx` 就断言未受理。
- 需要定义最少稳定字段：`operation`（`create_order` / `cancel_order`）、安全的失败类别（有限枚举或固定字符串）、可选 `status_code`。不要求提供响应全文、URL、token、Cookie、订单参数、用户标识或原始异常字符串。
- 异常消息、`str/repr`、SDK 主动日志应当不含账号、密码、验证码、token、含 token URL、Cookie、请求/响应正文。若需要保留调试关联信息，只允许新建非敏感标识，且**不得假称其是券商支持的幂等键**。
- 明确原始底层异常的处理方式及调试代价：不能为“保留异常链”而让标准 traceback 自动泄露带凭证的请求 URL。不能承诺宿主对任意第三方异常的自有打印、内存 introspection 或外部 APM 都可被 SDK 清洗。
- 不新建庞大的全局异常层级或统一 `Result[T]` 返回模型。若最小二类异常足以解决当前风险，Plan 应停止扩张。

**必须由维护者明确批准的兼容变更：** 新 `TradingClient` 在异常情况下的异常类型可能改变；Plan 应列出旧 `TradingClient` 原始异常类型与 P3 拟议异常的逐场景差异。**旧模块级 API 保持 P0/P1/P2 原样**，除非维护者另行批准破坏性兼容调整。

## 4. P3-B · 精确定义交易发送边界（最高优先级）

1. 明确区分认证阶段（验证码 GET、认证 POST、token GET）、交易发送前校验阶段、交易 POST、响应解码阶段。不能将**认证失败**误标为“下单结果未知”。
2. 只有实际进入或试图进入该次交易 POST 的调用链才允许触发 `TradeOutcomeUnknown`；从该边界开始，无论请求连接是否成功，都不能凭客户端异常确认未成交。
3. 在该边界之后：`requests.Timeout`、`ConnectionError`、`ChunkedEncodingError`、响应对象缺失/不合法、HTTP 非 200、3xx 响应、下单第一次/第二次 JSON 解码错误、撤单读取或处理文本错误，均需要明确的保守分类。不能在 3xx 情况下跟随重定向重新 POST。
4. 对于无异常且已取得符合原有成功路径的响应，仍返回原始 JSON / 文本结果，不擅自解释 `Status=-1`、订单号或业务拒绝字段，也不伪造“成交/拒绝已确认”。
5. 不因未知结果修改 token、强制自动重新登录、自动重试、自动查询、自动撤销、补单或恢复。是否在未知结果后允许**由调用方显式发起只读查询**，应写明契约；绝不自动转为重发交易。
6. 继续使用 P2 已有账户锁，保证整个 POST 与响应处理处于同账户临界区；异常抛出后锁必须释放，另一个实例能够继续执行合成测试任务。
7. 对新客户端查询、行情、认证阶段的 HTTP 非 200，Plan 应定义安全可诊断的非交易异常，但**不得**把查询异常误标为交易结果未知。已有 `TradingClient.login()` 失败清状态和认证策略保留。

### 最小 Kill Test（先写失败测试，再实现）

用实际 `TradingClient` 生产调用链，Mock **底层 Session**，不要 Mock 被测的 `_query_something()` / `create_order()`：

- **K1 认证失败**：新客户端未认证，认证 POST 抛 Timeout；断言交易 URL 的 POST **零次**，调用方得到认证失败的异常/返回，而非 `TradeOutcomeUnknown`。
- **K2 已就绪的订单**：交易 `session.post` 记录调用已发生后抛 Timeout；断言交易 POST **恰好一次**，抛机器可识别的 `TradeOutcomeUnknown`，不发生任何补偿查询或再次 POST。
- **K3 解析后失败**：下单第 2 次 JSON 解码抛异常、撤单 `text` 属性抛异常；均要标记未知、交易 POST 恰好一次。删除异常转换逻辑应导致对应测试失败。
- **K4 正常业务返回**：订单合成 `Status=-1` 等响应仍按原始契约返回，绝不宣称已拒绝或已成交，不产生额外 POST。

任一 Kill Test 不能满足，先修正发送边界设计，不扩展其它 API。

## 5. P3-C · 兼容与回归测试矩阵

| 场景 | 必须证明 |
| --- | --- |
| 认证前失败、关闭客户端、前置参数错误 | 无交易 POST；不错误标记交易结果未知 |
| 订单/撤单传输超时、连接异常、响应中断 | 业务 POST 至多一次；机器可识别的未知结果；不重试/补偿 |
| 订单 HTTP 4xx/5xx、3xx、响应 `None`/错误对象 | 保守未知分类；订单不跟随 307/308 重定向；不假定券商未受理 |
| 下单第 1/2 次 JSON 异常、撤单 text 异常 | 保留成功时的双解析/文本返回；失败统一风险信号；不重发 |
| 订单成功/合成业务拒绝 | 原始成功返回类型、值和字段不变；不擅自判断业务成败 |
| 查询/行情/认证 HTTP 错误 | 得到安全、可诊断的非交易错误，或 Plan 明确保留的原语义；不误归类交易未知 |
| 新客户端认证状态/close | 登录失败清 Cookie/token；失败后不得自动重登再发交易；锁释放、生命周期不回归 |
| 旧九项 API、`core.get_last_price`、CLI | 精确函数签名、返回/异常行为和已锁定测试接缝保持；旧 HTTP 裸 raise 行为如未单独批准不得改 |
| 敏感信息与变异测试 | SDK 主动日志、异常消息及标准 traceback 不暴露合成秘密；暂时移除转换/无重发保护可被新测试检出 |
| 测试执行与远端 CI | 继续系统级 `--network none`、合成父环境/凭证隔离、三种测试入口、完整 JUnit/coverage/日志 Artifacts |

P2 350 个历史节点及 P1 原 168 个节点应继续保留（或经独立审查证明等价迁移），不得删除、跳过或弱化既有风险断言来适配新异常。由于新客户端失败异常类型拟变更，允许**显式修改新客户端对应测试的异常预期**，但必须逐项注明修改前后语义与实际交易发送断言；不能直接全局放宽为 `Exception`。

## 6. 明确不在 P3 范围

- 不引入自动重试、幂等重发、补单、自动撤单、后台对账、订单状态轮询、成交确认自动化或真实券商查询；没有可信交易幂等协议时不许声称 exactly-once。
- 不猜测券商错误码或业务 `Status` 的真实含义；不修改 endpoint、表单字段、认证页面、OCR 算法或手续费/订单规则。
- 不修复旧模块级 API 的全局 Session/token、认证失败保留旧 token、裸 `raise` 等既存兼容风险；将其记录在后续独立批准事项中。
- 不添加默认 HTTP timeout、全局 retry 配置、统一 auth refresh、断线重连或跨进程协调；这些可能改变请求/结果语义，需另立阶段或独立批准。
- 不改 P2 账户隔离/锁算法、CLI、发布元数据、Python 最低版本、依赖主版本或建立 async/数据库/Redis/队列/持久化事件体系。
- 不引入真实账户测试或 CI 网络放行；不在自动化中访问券商。

## 7. Plan 交付与批准条件

使用新的 Plan Session，输出完整自包含 `docs/refactor/plans/P3-plan.md`，至少包括：

1. 实际 Git HEAD/工作区状态、既有 P2 文档归档是否合并、当前完整测试基线与相关文件调用图。
2. **兼容差异表**：新 `TradingClient` 的每个异常场景（包括登录前、POST 中、HTTP 返回后与 JSON/text 解码时），P2 当前异常、P3 期望异常；旧 API 明确不变。
3. **发送状态/信号模型**：如何精确识别是“尚无交易 POST”还是“交易尝试后结果未知”，并区分认证 POST 与交易 POST。要给出不会误分类的测试证据。
4. **公开异常设计**：名称、父类、可访问字段、字符串/日志行为及敏感信息控制；明确是否需要 `__cause__`、如何避免原始异常在 traceback 中泄露。
5. 直接修改共用 `_protocol.check_response` 的风险，以及如何保持 `core` 旧裸 raise；设计优先小范围分支或回调，不散布重复协议逻辑。
6. 测试列表与 Kill Test：真实生产链 seam、POST 精确计数、临界区与日志、安全变异；不得以 Mock 包装方法本身证明不重试。
7. 分批实施（每步独立验收及回滚）：错误契约测试 → 新客户端异常边界 → 订单/撤单风险异常 → 兼容/日志回归 → Linux 禁网/远端证据。
8. 拟修改文件清单、风险、证伪条件、停止条件，明确哪些涉及公开 API 需要维护者批准。

**Plan 输出不是 Build 授权。** 在计划明确异常兼容差异、风险分类、最小设计和测试失败条件后，再由维护者批准进入 Build。无真实协议证据时，任何试图自动确认订单结果的方案应被否决。
