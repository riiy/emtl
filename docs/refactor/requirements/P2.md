# P2 · TradingClient 状态隔离与并发安全（emtl）

> **状态：需求草案，供 `/emtl-plan P2` 使用；不是已批准的实施计划，也不授权立即修改生产代码。**
>

>
> 运行时基线：Python 3.11。**所有自动化验证必须离线、使用合成账户和 Mock，禁止真实登录、查询、下单、撤单。**

## 1. 事实基线与依赖文档

Plan 开始时阅读：

- 仓库根本地 `AGENTS.md`（如果存在；当前远端 `master` 未找到，不能假设已提交）及本地 `.opencode/commands/emtl-{plan,build,review}.md`（如果存在）。
- `docs/refactor/requirements/P0.md`、`docs/refactor/contracts/P0-public-api.md`、`docs/refactor/requirements/P1.md`、`docs/refactor/plans/P1-plan.md`、`docs/refactor/reports/P1-acceptance.md`。
- `src/emtl/core.py`、`src/emtl/__init__.py`、`src/emtl/const.py`、`src/emtl/cli.py`、`tests/`、`conftest.py`、`tox.ini`、`ci/offline.Dockerfile`、`.github/workflows/`。

已知源码事实（仍须以当前分支实际代码核实）：

1. `src/emtl/core.py` 模块级创建 `requests.Session()`、OCR 对象，并通过 `_em_validate_key` 保存全局 token；查询、下单、撤单复用这些可变状态。
2. `login()` 的现有行为包含环境变量回退、凭证 `strip()`、OCR、POST、获取验证 token；无匹配 token 时可能保留旧 token，业务 `Status` 未被解释。**这些是既有风险，不得在旧 API 上静默改变。**
3. `create_order()` 当前解析响应 JSON 两次；订单与撤单异常不会自动重试；HTTP 非 200 使用现有裸 `raise` 行为。旧 API 的兼容行为由 P0/P1 测试锁定。
4. `get_last_price()` 在 `core` 提供，但不在包级 `__all__` 中。现有包级九个函数及其签名、返回形状、CLI 行为均受兼容契约保护。
5. P1 已有 168 项离线用例及 Linux 网络命名空间禁网 CI；大量测试通过 monkeypatch 替换 `core.session`、`core._em_validate_key`、`core.login`、`core._query_something`。这些私有测试接缝可以迁移，但相同的**可观察行为与安全断言**不能丢失。

## 2. 最终目标

引入 **同步、显式绑定账户的 `TradingClient`**，将登录态、Cookie、HTTP Session 与验证 token 隔离到实例中；在同一 Python 进程内实现：

- **相同账户串行**：包括不同 `TradingClient` 实例指向同一账户的情况；保护认证、Cookie/token 更新和请求/响应处理关键区间。
- **不同账户允许并行**：不存在无必要的全局 HTTP 锁或共享 `requests.Session` / token；测试证明可并发进入各自的请求链。
- **旧 API 继续可用**：`import emtl; emtl.login(...); emtl.query_orders(); emtl.create_order(...); emtl.cancel_order(...)` 的原有签名和对外行为不发生未经批准的改变。
- **订单副作用保持至多一次发送尝试**：对于网络超时、连接中断、响应丢失、业务拒绝、解析异常，不自动补单、不自动撤单重试、不猜测交易是否成功。

交付目的是让调用方能够明确管理账户与会话，并为后续认证/异常改造建立安全边界；**不宣称真实券商协议已获验证，也不承诺跨进程分布式并发安全。**

## 3. P2 范围内（按优先级）

### P2-A · 新客户端的最小公开接口

1. 提供可从 `emtl` 导入的 `TradingClient`，例如 `from emtl import TradingClient`。允许在 `__all__` **末尾追加**该名称；既有九个导出名称的顺序与签名必须保持不变。此新增为 P2 明确批准的增量 API。
2. 客户端在构造时**绑定一个账户身份**；账户标识在实例生命期内不可悄然切换。Plan 明确构造参数、显式凭证与环境变量的优先级、账户身份规范化规则，以及认证凭证在内存中的保存方式；密码不得用于日志、`repr`、锁键或异常文本。
3. 新客户端暴露现有业务能力的同步方法：`login`、六项查询、`create_order`、`cancel_order`；行情 `get_last_price` 也须具备实例化的访问路径，避免复用其他账户的 HTTP 状态。
4. 推荐提供 `close()` 释放本实例所有的 HTTP Session 资源；重复调用安全。是否增加上下文管理器，由 Plan 按最小实现成本决策，不必同时引入 async API、连接池、插件系统或重型配置对象。
5. 明确依赖注入接缝（如允许为测试提供独立 Session / OCR 替身），但默认构建不得发起网络请求。不得意外把同一个 Session 共享给不同账户；若支持传入外部 Session，需文档化所有权及共享限制。

### P2-B · 实例状态隔离与认证边界

1. 每个客户端独立持有 `Session`、Cookie jar、token/认证状态，不从 `core` 的模块级可变 `session`/`_em_validate_key` 读取，不向它们写入。
2. 认证与请求在同一账户的锁保护下保持状态一致：绝不出现 A 账户 token 被拼到 B 账户 URL、A 的 Cookie 被 B 请求发送、A 的认证结果更新 B 的实例。
3. 新客户端的 `login` 对**失败或无法提取新 token**须采取明确定义的安全策略：不能将先前 token 当作本次认证成功；Plan 需详细规定失败判定、清空/保留 Cookie、返回/抛错等边界，并在合成响应下验证。对真实券商 `Status` 的含义未知时，不得编造成功或失败协议。
4. **新客户端与旧 API 的认证失败策略可以明确区分**：旧 API 的既有可观察行为必须兼容；如果计划将旧 API 委托到默认客户端，必须有逐项兼容证明。不得用“内部重构”掩盖旧 API 的失败语义变化。
5. 新客户端的验证码获取、登录和业务请求均必须有清晰的实例/Session 边界。当前 `core._get_captcha_code()` 使用模块级 `requests.get`，Plan 需明确新客户端如何避免因此引入跨实例共享状态，同时尽可能保持请求参数和现有超时行为。
6. 任何日志、异常和调试路径均不得主动输出用户名、密码、Cookie、Token、验证码、带 token 的 URL 或完整敏感响应。

### P2-C · 同账户串行 / 不同账户并行

1. 并发模型限定为**单进程内同步线程**；不引入 asyncio、多进程协调、Redis、数据库锁或分布式交易协调。
2. **同账户跨实例串行是硬性验收标准**。仅在 `self` 上添加 `Lock` 不能满足。Plan 必须设计同账户实例共享的最小锁协调方式，并说明身份 key 如何规范化、生命周期如何管理，避免使用密码作为 key 或造成不可控缓存增长。
3. 锁保护至少覆盖同账户认证状态读写、会话请求/响应、下单/撤单整个发送与响应处理区间；内部 `login()` 调用不得死锁。优先使用清楚的同步实现，不要设计多层锁或通用调度框架。
4. 不同账户分别持有 Session 和 token，可在确定性的并发测试中同时进入各自请求路径，不能被全局大锁串行化。
5. 锁只能保证**本进程内**对已知相同账户的调度；不能保证跨进程、跨设备、券商端的订单全局序列，也不能以此宣称“至多一次成交”。

### P2-D · 旧 API 兼容迁移

1. 既有九个包级函数保持**精确签名、参数默认值、请求字段、成功返回类型、异常传播和可观察调用行为**。`emtl.core.get_last_price()` 与 CLI 入口继续有效。
2. Plan 应比较以下两种最小方案：**单一实例化实现 + 旧 API 兼容包装层**；或**新实例化实现与最小遗留兼容层并存**。明确推荐一种并给出兼容迁移证据，不允许长期维护两套无法校验的协议逻辑。
3. 如果将旧调用包装为一个默认客户端，需明确默认账户/重新登录时的 Session、Cookie 和 token 变化，特别是旧 API 登录失败保留 token 的既有特征；不能误宣称旧模块级接口天然支持多账户并发。
4. P1 对 `core.session` / `_em_validate_key` 等内部实现的 monkeypatch 测试允许做**等价迁移**，但必须列出逐项映射表：原测试 → 新测试接缝 → 保留的行为/风险断言。不得删除、跳过、弱化订单请求次数、日志脱敏、异常传播或网络禁用测试以换取绿灯。
5. 不破坏 `pytest` 既有启动时隔离/恢复、tox 环境隔离、Docker `--network none`、CI Artifacts 收集。新类及其测试不能绕过 P1 安全网。

## 4. 明确不在 P2 范围

- 不修改券商 HTTP endpoint、交易参数名称、行情/交易字段 schema 或无可靠证据的业务错误码解释。
- 不增加下单或撤单自动重试、自动补单、自动确认、幂等推断、自动恢复/补偿性操作；交易结果不确定时原样传播或使用经明确批准的新客户端错误语义。
- 不做系统化异常层级、返回模型重写、超时/重试策略升级、OCR 算法优化、递归重试整治、全面认证协议升级（这些归后续阶段）。
- 不引入 async、分布式账户锁、数据库/队列、线程池管理器、复杂依赖注入容器，也不以“100% 覆盖率”为目标。
- 不进行真实账户端到端测试、不修改自动测试为可连公网、不执行真实交易、不自动发布 PyPI。
- 不做无关的 README 全面重写、打包迁移或第三方依赖大版本升级。

## 5. 最小前置 Kill Test（Plan 必须设计）

在重构所有 API 之前，用纯合成 Mock/事件协调验证最关键的技术假设：

1. 同账户 A 的两个实例，线程 1 在请求关键区间被受控事件阻塞；线程 2 在释放前**不能**进入同账户 HTTP 发送阶段。
2. 不同账户 A 与 B，各自 HTTP 假实现可在受控事件/Barrier 下**同时**进入请求关键区间；不存在全局锁阻塞。
3. 两个账户带不同 token/Session/Cookie 哨兵，请求的 URL、headers 和 Cookie 不出现交叉泄漏。

测试必须使用 `threading.Event` / `Barrier` 等确定性协调；不以 `sleep()` 和运气作为并发正确性的主要证据。**任意一项失败，停止扩大业务 API 迁移，修正隔离设计后重新验证。**

## 6. P2 测试矩阵与验收门槛

| 领域 | 最小场景 | 必须断言 |
| --- | --- | --- |
| 独立实例 | 账户 A/B 各自认证、查询、订单调用 | Session、Cookie、token、URL 不交叉；没有模块全局状态污染 |
| 同账户两实例 | 两线程交错登录/查询/委托 | 请求关键区间不重叠，锁无死锁 |
| 异账户两实例 | 两线程并发查询 | 请求关键区间允许重叠，无全局串行瓶颈 |
| 登录失败 | 无 token、无效合成响应、传输异常、先成功后失败 | 新类失败策略明确且 fail-closed；旧 API 语义仍按契约保留 |
| 资金风险 | 下单/撤单 Timeout、ConnectionError、响应丢失、JSON/text 异常、业务拒绝 | 每次调用最多一次 POST 发送尝试，无静默重试、无交叉账户执行 |
| 查询与行情 | 六查询、历史字段、价格异常/NaN | 表单、返回、异常传播保持兼容；新客户端使用自身 Session |
| CLI / 旧导出 | 全部九函数、`get_last_price`、`emt`、`python -m emtl` | 既有签名/语义不变；`TradingClient` 作为明确新增接口 |
| 测试安全 | 根 pytest、仓库外测试、tox、Linux `--network none` | 不触网、无凭证、完整结果及证据可审计 |

测试数量与总体覆盖率仅为观察指标；不以增加 N 项或达到某个百分比代替上述断言。P1 的既有 168 项应继续通过，或明确等价迁移且保持/加强同等覆盖，禁止无说明地删减。

## 7. Plan 交付要求

`/emtl-plan P2` 应生成完整、自包含、可以跨会话执行的 `docs/refactor/plans/P2-plan.md`，至少包含：

1. 当前 Git HEAD、工作区状态、事实依据、模块/调用图和 P1 回归基线。
2. **新客户端公开 API 草案**：构造参数、账户身份、凭证、生命周期、方法、同步模型、返回/异常行为及示例。
3. **旧 API 逐函数迁移表**：已有签名和关键行为、新类对应方法、潜在差异、保持兼容的验证方式。
4. **状态所有权表**：Session、Cookie、token、OCR、账户锁、默认客户端、环境变量属于哪里，何时创建/更新/销毁。
5. **锁设计与不变量**：单实例/跨实例同账户锁、身份 key、锁生命周期、可重入问题、不同账户并行、失败后释放。
6. **认证状态转换表**：首次登录、重复登录、失败、网络异常、无 token、主动关闭；新类与旧 API 的差异单独写明。
7. **P1 测试接缝迁移表**：列出涉及私有 `core.*` patch 的测试、迁移方案和保留断言；明确不会通过 Mock 被测函数本身证明安全。
8. 分小批次的 Build 顺序：最小 Kill Test → 独立 Session/Token → 同账户锁 → 新客户端方法 → 旧 API 兼容迁移 → 全量回归及 CI；每步有失败停止条件、回滚方式。
9. 可验证的文件修改清单、离线测试命令、Linux CI 验收证据、Review 清单及未决风险。分析阶段不修改生产代码。

如旧 API 的完整语义与新的 fail-closed 策略不能安全共用一个实现，**Plan 应显式揭示冲突并提出最低成本兼容方案，等人工批准后再 Build**，而不是擅自改变旧行为。

## 8. Build 执行边界

- 仅执行已批准并保存的 `P2-plan.md`；每个里程碑完成独立测试后再继续。
- 任何拟改变旧 API 的签名、返回/异常语义、网络参数、交易请求次数、CLI 行为的事项，必须暂停并单独申请批准。
- 新增 P2 测试可以与生产代码同步，但不得删除安全断言；不因绿灯就跳过 Docker/CI 验证。
- 严格限制 `src/emtl/` 修改为状态隔离和必要的兼容包装；不提前实现 P3/P4。
- 不主动提交、推送、触发真实交易或发布；由维护者控制 Git 操作。

## 9. 独立 Review / PASS 标准

Review 必须检查 tracked、staged、untracked，核对实际源码、测试、Plan 与验收证据，至少回答：

1. `TradingClient` 两个不同账户实例是否真的没有共享可变 Session、Cookie、token？
2. **两个实例代表同一账户时**，是否真的串行，而不只是同一对象内加锁？
3. 不同账户是否确实并行？测试是 Event/Barrier 的确定性证明还是脆弱计时？
4. 新客户端失败登录是否阻止旧 token 被误用？旧接口失败登录行为是否未经授权改变？
5. 是否保留所有资金副作用的**一次 POST**与不自动重试断言？
6. P0/P1 测试、契约、日志脱敏、禁网和 CI 是否保持；所有变更测试的风险断言是否能映射？
7. 生产路径是否引入全局瓶颈、复杂框架或不可控锁注册表增长？
8. 远端 GitHub Actions 最终提交的 CI、网络模式、JUnit/coverage 与 artifacts 是否可核验？

符合上述要求，证据对应最终代码版本且无高严重度问题，方可 `PASS`；存在确定的隔离/重复下单/兼容性缺陷应 `FAIL`；仅欠远端证据应 `NEEDS EVIDENCE`。不能用本地 `PASS` 冒充远端验收。

## 10. 结束与停止条件

当以下条件都满足时**停止 P2，不继续追加技术债清理**：

- 独立多账户 `TradingClient` 可用，同账户跨实例串行、不同账户并行测试通过；
- 旧 API/CLI 按批准的兼容边界继续可用；
- 资金副作用单次发送、异常传播及敏感信息安全断言通过；
- 离线 Linux CI 及证据交付闭环，独立 Review 为 PASS。

尚未解决的券商真实认证语义、跨进程并发、旧 token 清理全面升级、异常体系等进入后续风险列表，不因 P2 工程通过而宣称安全覆盖。
